# Technical Design Document (TDD)

**Проект:** Project Artifact  
**Версия:** 0.1  
**Статус:** предварительная техническая концепция

Документ фиксирует технические требования, вытекающие из текущего GDD. Это не окончательная архитектура: реализация уточняется после прототипирования.

## 1. Целевые платформы

- Windows PC.
- Android.

Игра должна учитывать различия устройств ввода, разрешений экрана и производительности. Предпочтительная ориентация Android — Landscape.

## 2. Игровой движок

**Godot Engine 4** — предварительный кандидат.

Причины для проверки:
- инструменты для 2D-игр;
- сцены, узлы и ресурсы;
- анимация, физика и коллизии;
- возможность создания изометрических сцен;
- экспорт на Windows и Android;
- отсутствие лицензионных отчислений за использование движка.

Выбор не окончательный. До начала масштабной разработки необходимо собрать небольшой прототип и проверить экспорт на обе целевые платформы.

Официальный сайт: https://godotengine.org/

## 3. Архитектурные подсистемы

Предварительно проект следует разделить на следующие области ответственности:

| Подсистема | Ответственность |
|---|---|
| Game Flow | Последовательность глав, фаз и сюжетных переходов |
| Character System | Состояние персонажа, движение и способности |
| Combat System | Атаки, защита, противники и боссы |
| World State | Состояния интерактивных объектов и окружения |
| Level System | Сцены, геометрия, переходы и триггеры |
| Narrative / Quest System | Сюжетные события, диалоги и флаги |
| Save System | Сохранение прогресса и состояния мира |
| Input System | Абстракция PC-, gamepad- и touch-ввода |
| UI System | Игровой интерфейс и меню |
| Audio System | Музыка, окружение и звуковые эффекты |

Это логическое разделение. Оно не требует создавать отдельный глобальный менеджер для каждой подсистемы: реализация должна оставаться простой и соответствовать возможностям движка.

## 4. Персонажи и режимы управления

У каждого героя должны быть собственные параметры движения, способности, анимации и боевая логика.

Общие технические компоненты можно переиспользовать, но различия геймплея должны оставаться явными.

Возможные общие компоненты:
- получение пользовательского ввода;
- обработка здоровья и урона;
- базовые состояния анимации;
- взаимодействие с объектами;
- система эффектов;
- регистрация событий.

Специфические способности не следует искусственно сводить к одному универсальному набору действий.

## 5. Общие локации и сценарные фазы

Общая локация представляет одну сцену или логически связанную группу сцен с общими идентификаторами объектов.

Обязательная последовательность прохождения:

1. ROGUE_PHASE
2. KNIGHT_PHASE
3. MAGE_PHASE

Переходы между фазами выполняются Game Flow / сценарным контроллером, а не свободным выбором игрока.

### 5.1. Модель интерактивного объекта

Каждый объект, состояние которого влияет на дальнейшее прохождение, должен иметь:
- стабильный object_id;
- исходное и текущее состояние;
- перечень допустимых взаимодействий;
- ограничения по активному персонажу или фазе;
- результат взаимодействия;
- возможность сериализации для сохранения.

Названия состояний определяются конкретным объектом. Не требуется использовать одинаковую таблицу состояний для всех объектов.

### 5.2. Последовательность и блокировки

Система должна:
- разрешать действия только активной фазе и персонажу;
- сохранять результаты действий предыдущего героя;
- запускать следующую фазу только по сценарию;
- проверять обязательные условия перехода;
- предотвращать состояния, из которых невозможно продолжить обязательное прохождение;
- корректно восстанавливать фазу после загрузки сохранения.

### 5.3. Хронология

Не все сюжетные события относятся к одному и тому же моменту времени. Поэтому состояние мира должно учитывать контекст события и конкретную локацию.

Необходимо различать:
- локальные изменения общей локации между последовательными прохождениями;
- события индивидуальных сюжетных глав;
- последствия эпизодических встреч;
- глобальные сюжетные флаги.

Нельзя автоматически переносить изменение из одной сюжетной линии в другую, если это противоречит хронологии.

Полная модель времени и синхронизации пока не определена и должна быть спроектирована на конкретных сюжетных примерах.

## 6. Сохранения

Система сохранений должна учитывать как минимум:
- текущую главу и локацию;
- активного персонажа;
- текущую фазу общей локации;
- состояние интерактивных объектов;
- прогресс головоломок;
- сюжетные флаги;
- прогресс персонажей и разблокированные способности;
- предметы и другие данные прогресса, если соответствующие системы будут утверждены.

Сохранение не должно ограничиваться координатами персонажа. После загрузки игра должна восстановить согласованное состояние локации и сюжетной последовательности.

Формат данных и частота автосохранения будут определены при реализации.

## 7. Камера и графические режимы

Текущая концепция предусматривает:
- изометрическое исследование;
- платформенные участки с видом сбоку;
- преимущественно боковой боевой режим Воина;
- предполагаемый изометрический бой Вора и Мага;
- изометрические сцены транспорта.

Прототип должен проверить переходы между перспективами, корректность коллизий, сортировку объектов по глубине в изометрии, стабильность управления и совместимость разных режимов с одной системой локаций.

## 8. Управление и ввод

Рекомендуется отделить игровые действия от конкретного устройства ввода.

Один набор игровых действий должен поддерживать:
- клавиатуру и мышь;
- геймпад;
- сенсорные элементы Android.

Схемы управления должны быть настраиваемыми. Для Android необходимо проверить размеры интерактивных элементов и удобство одновременного управления движением и действиями.

## 9. Pixel Art и графические ресурсы

Графические ресурсы следует организовать по категориям:
- персонажи и их анимации;
- противники и боссы;
- тайлы и окружение;
- интерактивные объекты;
- эффекты атак, магии и разрушений;
- интерфейс;
- шрифты.

До производства большого объёма графики необходимо определить базовое разрешение спрайтов, размер тайлов, масштаб отображения, палитру и правила анимации.

## 11. Нефункциональные требования

- Стабильная работа на Windows PC и поддерживаемых Android-устройствах.
- Масштабируемый интерфейс.
- Сохранение и восстановление состояния прохождения.
- Отсутствие блокирующих ошибок в обязательных сюжетных последовательностях.
- Предсказуемая работа коллизий и интерактивных объектов.
- Возможность тестировать отдельные сцены и подсистемы независимо.
- Контроль версий для исходников, ресурсов и документации.

Минимальные системные требования, целевая частота кадров и список поддерживаемых Android-устройств пока не определены.

## 12. Технические риски

1. **Несколько перспектив и режимов боя.** Проверить совместимость камер, коллизий, анимаций и управления до производства контента.
2. **Состояние общих локаций.** Сразу предусмотреть идентификаторы объектов и сериализацию изменений.
3. **Хронология сюжетных линий.** Не смешивать локальные изменения общей локации и события, происходящие в разные моменты истории.
4. **Обязательная последовательность прохождения.** Проверять все переходы и исключать блокировки прогресса.
5. **Android.** Рано проверить сенсорное управление, производительность и масштабирование интерфейса.
6. **Объём графики.** Уникальные анимации трёх героев и разные режимы требуют раннего определения художественных стандартов.
